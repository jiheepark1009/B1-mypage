### 3-2. Flexbox vs Grid — 왜 나눠 썼는가 (#13, FAIL 항목)

▶ 화면: `.nav` (225행) → `.projects__grid` (539행)

💬 "레이아웃은 상황에 따라 Flexbox와 Grid를 나눠 썼습니다. 기준은 하나입니다. **'한 줄(1차원) 정렬이냐, 행과 열(2차원) 배치냐.'**"

💬 "네비게이션은 로고, 메뉴, 버튼이 **한 줄 안에서** 양쪽 끝으로 벌어지기만 하면 됩니다. 그래서 Flexbox의 `justify-content: space-between`을 썼습니다. 반대로 프로젝트 카드는 개수와 화면 폭이 계속 바뀌고, 한 줄에 몇 개가 들어갈지 자동으로 계산되어야 합니다. 행과 열이 동시에 필요한 2차원 배치라서 Grid를 썼고, `repeat(auto-fit, minmax(280px, 1fr))` 한 줄로 '최소 280px은 보장하고, 남는 공간은 나눠 갖고, 안 들어가면 다음 줄로'라는 규칙을 만들었습니다. 이러면 미디어쿼리 없이도 카드 개수가 화면 폭에 맞게 자동으로 바뀝니다."

💬 "참고로 Flex 컨테이너 안의 자식은 원래 인라인 요소(`<a>` 같은)여도 flex item이 되어 크기와 정렬을 마음대로 줄 수 있습니다. 이것도 Flex를 쓴 이유 중 하나입니다."

### 3-3. 모바일 퍼스트와 브레이크포인트 (#1, #15)

▶ 화면: `@media (min-width: 768px)` (921행), `@media (min-width: 1024px)` (977행)

💬 "반응형은 모바일 퍼스트로 작성했습니다. 기본 CSS가 가장 좁은 화면 기준이고, `min-width: 768px`, `1024px`에서 필요한 스타일만 추가하는 방식입니다. 반대로 데스크톱 기준으로 먼저 만들고 `max-width`로 줄이면 모바일에서 쓰지도 않을 스타일을 먼저 읽고 덮어써야 해서 코드가 꼬입니다. 768px 미만에서는 메뉴를 숨기고 햄버거 버튼을 보여주고, 768px 이상에서는 반대로 바뀝니다."

**[평가 #1 '부족한 점' 대응]** "브레이크포인트별 스크린샷은 README에 아직 못 넣었습니다. 데스크톱, 태블릿, 모바일 캡처를 추가하는 것이 다음 보완 항목입니다."

## 4. JavaScript — DOM, 이벤트, 인터랙션 (2분) — 평가 #9, #3, #2

### 4-1. 기본 흐름 (#9)

▶ 화면: `js/main.js` 40행 `navToggle.addEventListener`

💬 "JS의 기본 흐름은 항상 세 단계입니다. `querySelector`로 요소를 **선택**하고, `addEventListener`로 이벤트를 **연결**하고, 이벤트가 발생하면 `classList`나 `textContent`로 **DOM을 바꿉니다.** HTML에 `onclick`을 직접 쓰지 않고 전부 JS 파일에서 연결한 이유는, 구조(HTML)와 동작(JS)을 섞지 않기 위해서입니다."

💬 "햄버거 메뉴가 대표적인 예입니다. 버튼을 클릭하면 `classList.toggle('is-open')`으로 클래스만 붙였다 뗍니다. 실제로 메뉴가 보이고 사라지는 것, 아이콘이 X로 바뀌는 것은 전부 CSS가 그 클래스를 보고 처리합니다. **JS는 상태(클래스)만 바꾸고, 화면은 CSS가 그린다**는 역할 분리입니다."

### 4-2. 부드러운 스크롤과 preventDefault (#3)

▶ 화면: 54~55행 `anchorLinks.forEach`

💬 "앵커 링크 `<a href="#about">`는 원래 클릭하면 애니메이션 없이 즉시 점프합니다. 부드럽게 이동시키려면 이 **기본 동작을 먼저 막아야** 해서 `event.preventDefault()`를 쓰고, 대신 `scrollIntoView({ behavior: 'smooth' })`로 직접 이동시킵니다. 이때 모바일 메뉴도 함께 닫아줍니다."

### 4-3. 스크롤 이벤트 두 가지를 한 리스너로 (#3)

▶ 화면: 73~85행 `handleScroll`

💬 "스크롤 이벤트는 굉장히 자주 발생합니다. 그래서 리스너를 하나만 두고, `requestAnimationFrame`으로 화면 프레임당 한 번만 실행되게 제한했습니다. 이 안에서 두 가지를 처리합니다. 60px 이상 내려가면 네비게이션 배경을 바꾸고, 300px 이상이면 맨 위로 버튼을 보여줍니다. 이 기준값은 상수로 빼서 README에도 적어두었습니다."

### 4-4. 스크롤 애니메이션 (#3)

▶ 화면: 376행 `revealObserver`

💬 "스크롤 애니메이션은 `scroll` 이벤트로 위치를 계산하는 대신 `IntersectionObserver`를 썼습니다. 브라우저가 '이 요소가 화면에 몇 % 보이는지'를 알려주기 때문에 계산 부담이 없습니다. `threshold`는 0.2로, 요소가 20% 보이면 등장시킵니다. 한 번 보여준 요소는 `unobserve`로 감시를 끊어서 불필요한 작업을 막았습니다."

**[평가 #3 '부족한 점' 대응]** "모바일 메뉴에 ESC 키로 닫기나 포커스 이동은 아직 구현하지 않았습니다. 지금은 `aria-expanded`로 열림 상태만 알려주고 있고, 키보드 접근성은 다음 개선 항목입니다."

### 4-5. 다크모드 저장 (#2)

▶ 화면: `index.html` 16행 head 인라인 스크립트 → `main.js` 28행

💬 "다크모드는 버튼을 누르면 `data-theme` 속성을 바꾸고, 같은 값을 `localStorage`에 저장합니다. 새로고침하면 저장된 값을 읽어 복원합니다. 여기서 한 가지 신경 쓴 게, 이 복원 코드를 `<head>` 맨 위 짧은 인라인 스크립트에 뒀다는 점입니다. 이걸 `main.js`에만 두면 '라이트로 먼저 그렸다가 다크로 바뀌는' 깜빡임이 생기기 때문입니다. 저장된 값이 없으면 `prefers-color-scheme`으로 사용자 OS 설정을 따릅니다."

## 5. ES6+ 문법과 비동기 처리 (2분) — 평가 #12, #4, #11

### 5-1. 배열 메서드 (#12)

▶ 화면: 198행 `createProjectCard`, 221행 `renderFeaturedProjects`, 229행 `filterButtons.forEach`

💬 "카드는 HTML에 하나씩 쓰지 않고, 데이터 배열을 만들어서 JS로 그렸습니다. 데이터만 바꾸면 화면이 바뀌기 때문에 나중에 실제 프로젝트로 교체하기 쉽습니다. 이때 세 가지 배열 메서드를 목적에 따라 나눠 썼습니다."

💬 "`map`은 각 데이터를 카드 HTML로 **바꿔서 새 배열**을 만들 때, `filter`는 카테고리에 맞는 것만 **골라낼** 때, `forEach`는 결과 배열이 필요 없고 버튼마다 이벤트를 **등록하기만** 하면 될 때 썼습니다. 리턴값이 필요한지 여부가 구분 기준입니다."

💬 "함수는 화살표 함수를 썼고, 매개변수에서 구조분해 할당으로 필요한 필드만 바로 꺼냈습니다. GitHub API 응답은 필드가 20개가 넘는데, `({ name, description, html_url: htmlUrl, ... })`처럼 쓰면 이 함수가 어떤 데이터를 쓰는지 한눈에 보입니다. 카드 HTML은 템플릿 리터럴로 만들었습니다."

**[평가 #12 '부족한 점' 대응]** "카드가 수천 개가 되면 가상화 같은 성능 최적화가 필요하지만, 이 사이트는 카드가 4~6개라서 반영하지 않았습니다."

### 5-2. fetch + async/await + 4가지 상태 (#4, #11)

▶ 화면: 271행 `loadRepos`

💬 "Projects 섹션 아래의 GitHub 저장소 카드는 `fetch`로 GitHub API를 호출해서 그립니다. 네트워크 요청은 시간이 걸리기 때문에 비동기로 처리해야 하고, `async/await`를 쓰면 위에서 아래로 읽히는 순서 그대로 코드를 쓸 수 있습니다."

💬 "API 연동에서 중요한 건 성공만 가정하지 않는 겁니다. 그래서 네 가지 상태를 전부 화면으로 표현했습니다. **로딩**은 스켈레톤 카드와 '불러오는 중' 문구, **성공**은 카드 렌더링, **빈 상태**는 '표시할 프로젝트가 없습니다', **에러**는 '불러올 수 없습니다' 문구와 재시도 버튼입니다."

💬 "에러 처리는 `try/catch`로 했습니다. 응답이 `ok`가 아니면 직접 에러를 던져서 `catch`로 넘기고, 특히 403이면 GitHub의 시간당 60회 호출 제한(rate limit)에 걸린 것이라서 그 사실을 문구에 함께 알려줍니다. 재시도 버튼을 누르면 `loadRepos`를 다시 호출합니다."

**[평가 #4, #11 '부족한 점' 대응]** "지금은 rate limit인지 일반 실패인지만 구분하고 있고, `console.error`로 응답 코드를 남기는 로깅이나 '몇 분 뒤 다시 시도' 같은 구체적 안내는 없습니다. 에러 유형별 문구를 더 세분화하고 로깅을 추가하는 것이 보완점입니다."

## 6. 폼 검증과 상태 흐름 (1분) — 평가 #5, #10, #14

### 6-1. 폼 검증 (#5)

💬 "폼은 이름, 이메일, 메시지 세 필드에 각각 검증 규칙을 객체 하나(`fieldRules`)로 묶어서 관리했습니다. 필드마다 '검증 함수'와 '에러 메시지'가 짝으로 있어서, 필드가 늘어나도 규칙만 추가하면 됩니다. 이메일은 정규식으로 형식을 검사하고, 입력할 때마다(`input` 이벤트) 실시간으로 에러를 지우거나 보여줍니다. 제출(`submit`)할 때는 `preventDefault()`로 페이지 새로고침을 막고 전체를 다시 검증한 뒤, 통과하면 성공 메시지를 보여줍니다. 에러는 각 입력창 바로 아래에 표시됩니다."

## 부록 A. 예상 질문 & 답변

**Q1. 왜 프레임워크 없이 만들었나요?**
A. 미션의 목적이 React 이전에 DOM 조작·이벤트·비동기를 체득하는 것이기 때문입니다. React의 컴포넌트와 상태는 이 과정을 자동화한 것이라, 먼저 손으로 해봐야 React가 무엇을 대신해주는지 이해할 수 있다고 생각했습니다.

**Q2. `var` 대신 `const`/`let`을 쓴 이유는?**
A. `var`는 함수 스코프라 블록 밖에서도 값이 살아있어 의도치 않은 버그가 생길 수 있습니다. `const`/`let`은 블록 스코프이고, 값이 바뀌지 않는 건 `const`로 명시해서 '이 값은 바뀌면 안 된다'는 의도를 코드로 보여줍니다. 이 프로젝트에서 재할당이 필요한 건 스크롤 throttle 플래그(`isScrollTicking`) 정도라 대부분 `const`입니다.

**Q3. `innerHTML`을 쓰면 XSS 위험이 있지 않나요?**
A. 맞습니다. 사용자가 입력한 값을 `innerHTML`에 넣으면 위험합니다. 이 프로젝트에서 `innerHTML`에 들어가는 값은 제가 작성한 데이터 배열과 GitHub API 응답입니다. 다만 API 응답의 `description` 같은 외부 문자열을 그대로 넣고 있어서, 엄밀하게는 `textContent`로 넣거나 이스케이프 처리를 하는 것이 더 안전합니다. 폼 입력값은 `innerHTML`이 아니라 `textContent`로만 화면에 넣었습니다.

**Q4. `classList.toggle`과 `add`/`remove`를 나눠 쓴 이유는?**
A. 현재 상태를 뒤집으면 되는 곳(햄버거, 다크모드 아이콘)은 `toggle`, 상태를 명확히 지정해야 하는 곳(링크 클릭 시 메뉴 닫기, 필터 버튼 active 초기화)은 `add`/`remove`를 썼습니다. 링크 클릭 후에는 메뉴가 '반드시 닫혀야' 하므로 toggle을 쓰면 이미 닫힌 상태에서 열리는 버그가 생길 수 있습니다.

**Q5. 스크롤 이벤트에 `requestAnimationFrame`을 쓴 이유는?**
A. 스크롤은 초당 수십~수백 번 발생합니다. 매번 DOM을 바꾸면 렌더링이 버벅이기 때문에, 브라우저가 화면을 그리는 주기(프레임)에 맞춰 한 프레임에 한 번만 실행되도록 했습니다.

**Q6. 왜 `IntersectionObserver` threshold를 0.2로 했나요?**
A. 미션 권장값이 0.2 이상이었고, 요소가 너무 조금 보일 때(예: 5%) 애니메이션이 시작되면 사용자가 인지하기 전에 끝나버리기 때문입니다. 20% 정도 보일 때 시작하면 자연스럽게 등장하는 모습이 보입니다.

**Q7. GitHub API를 인증 없이 호출해도 되나요?**
A. 인증 없이는 시간당 60회 제한이 있습니다. 개인 포트폴리오는 방문이 적어서 충분하고, 제한에 걸리면(403) 에러 상태와 재시도 버튼으로 처리했습니다. 토큰을 쓰면 제한이 풀리지만, 프론트엔드 코드에 토큰을 넣으면 노출되기 때문에 사용하지 않았습니다.

**Q8. `event.preventDefault()`는 각각 왜 쓰나요?**
A. 앵커 링크는 기본 동작이 '즉시 점프'라서 부드러운 스크롤을 하려면 막아야 하고, 폼은 기본 동작이 '페이지 새로고침(서버 전송)'이라서 JS 검증을 하려면 막아야 합니다.

**Q9. `data-*` 속성(dataset)은 왜 썼나요?**
A. 필터 버튼이 어떤 카테고리를 뜻하는지를 HTML에 `data-filter="marketing"`으로 적어두고, JS에서는 `btn.dataset.filter`로 읽습니다. 버튼마다 별도 함수를 만들지 않고 리스너 하나로 처리할 수 있고, 카테고리를 추가할 때 HTML만 고치면 됩니다. 숫자 카운트업의 목표값(`data-count-to`)도 같은 방식입니다.

**Q10. 인라인 스타일을 안 쓴 이유는?**
A. 스타일을 HTML 안에 쓰면 다크모드나 반응형처럼 CSS 변수와 미디어쿼리로 한 번에 바꾸는 구조가 깨집니다. 모든 스타일은 `css/style.css`에서만 관리해서 한 곳만 고치면 되게 했습니다.

**Q11. 사전평가에서 FAIL이 나온 두 항목은 어떻게 할 건가요?**
A. (#13) Flex vs Grid 선택 근거는 코드에는 반영되어 있었지만 README에 서술하지 않았습니다. README에 '1차원 정렬은 Flex, 2차원 카드 배치는 Grid'라는 기준을 추가하겠습니다. (#14) 상태가 DOM과 함수 인자에 분산되어 있어서, `STATE` 객체 하나로 모으고 `render()`가 그것을 읽어 그리는 구조로 리팩터링하겠습니다.
