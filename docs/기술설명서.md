# 기술 구현 설명서 — 박지희 포트폴리오 웹사이트

이 문서는 `index.html` / `css/style.css` / `js/main.js`를 만들면서 **왜 그렇게 짰는지**를 기초 개념부터 정리한 문서입니다. 동료 평가에서 "이거 왜 이렇게 만들었어요?"라는 질문에 바로 답할 수 있도록, 각 챕터는 (1) 기본 개념 → (2) 이 프로젝트에 적용한 방식 → (3) 실제 코드 순서로 구성했습니다.

---

## 1. HTML — 시맨틱 태그와 구조 설계

### 1-1. 시맨틱 태그를 쓰는 이유

`<div>`는 브라우저 입장에서 "그냥 상자"입니다. 안에 뭐가 들었는지, 페이지에서 무슨 역할을 하는지에 대한 정보가 전혀 없습니다. 반면 `<header>`, `<nav>`, `<main>`, `<section>`, `<footer>` 같은 시맨틱 태그는 **역할이 이름에 박혀 있습니다.**

이게 실제로 왜 중요하냐면:

- **스크린리더**가 "여기부터 네비게이션이다", "여기부터 본문이다"를 안내할 수 있음 (접근성)
- **검색엔진**이 페이지 구조를 이해해서 검색 결과 품질에 영향을 줌 (SEO)
- **개발자 본인**도 6개월 뒤에 코드를 다시 봤을 때 `<div class="wrapper"><div class="inner">` 지옥보다 `<section id="projects">`가 훨씬 빨리 읽힘

### 1-2. 인라인 요소 vs 블록 요소

구조를 짤 때 계속 신경 쓴 기본 개념 하나가 **인라인(inline) vs 블록(block)** 입니다.

| 구분 | 특징 | 예시 |
| --- | --- | --- |
| 블록 요소 | 항상 새 줄에서 시작, 가로 폭을 꽉 채움, width/height 지정 가능 | `div`, `section`, `header`, `footer`, `ul`, `p`, `form` |
| 인라인 요소 | 줄 안에서 텍스트처럼 흐름, width/height 지정이 의미 없음(내용 크기만큼만 차지) | `span`, `a`, `i`, `strong`, `label` |

이 프로젝트에서 이 개념이 실제로 쓰인 지점:

- `.nav__logo`는 원래 인라인 요소인 `<a>` 태그입니다 ([index.html:29](index.html:29)). 그런데 부모인 `.nav`에 `display: flex`를 걸어두면([css/style.css:225](css/style.css:225)), **자식 요소는 원래 태그가 인라인이든 블록이든 상관없이 flex item으로 취급됩니다.** 그래서 `<a>` 태그인데도 로고가 원하는 크기의 박스처럼 배치될 수 있는 겁니다.
- 버튼(`<button>`)도 기본은 인라인 요소에 가깝지만, `.btn` 클래스에서 `display: inline-flex`를 줘서([css/style.css:168](css/style.css:168)) 아이콘과 텍스트를 가로로 정렬하면서도 다른 텍스트 흐름 안에 자연스럽게 놓일 수 있게 했습니다.

### 1-3. 이 프로젝트의 구조 설계 기준

섹션을 나눈 기준은 "사용자가 이 페이지를 처음 본 순간부터 마음이 움직이는 순서"입니다.

```
header (nav)          → 언제든 다른 섹션으로 이동 가능해야 함
main
 ├─ section#hero       → 3초 안에 "누구인지 + 무슨 일을 하는지" 전달
 ├─ section#about      → "왜 이 일을 하는지"에 대한 신뢰 쌓기
 ├─ section#skills     → "실제로 할 줄 아는 것"을 증명
 ├─ section#projects   → "결과물"로 증명 마무리
 └─ section#contact    → 행동 유도(CTA)
footer                 → 저작권 + 소셜 링크
```

`div`로 전체를 감싸지 않고 `header > nav`, `main > section`, `footer`로 나눈 이유가 이 흐름과 일치합니다 — 즉 **콘텐츠의 의미 단위 = 시맨틱 태그 단위**로 맞췄습니다.

접근성 관련해서 신경 쓴 부분 2가지:

- 모든 `<img>`에 "무엇을 보여주는 이미지인지" 설명하는 `alt`를 넣었습니다. 장식용이 아니라 정보 전달용 이미지(프로필, 프로젝트 그래픽)이기 때문에 `alt=""`로 비워두지 않았습니다.
- `<label for="name">`과 `<input id="name">`처럼 `for`와 `id`를 정확히 매칭했습니다([index.html:163](index.html:163)). 이렇게 하면 라벨 텍스트를 클릭해도 입력창에 포커스가 가고, 스크린리더가 "이름 입력란입니다"라고 읽어줍니다.

## 2. CSS — Flexbox와 Grid, 언제 무엇을 쓰는가

### 2-1. 핵심 차이

| | Flexbox | Grid |
| --- | --- | --- |
| 축 | 1차원 (가로 **또는** 세로 한 줄) | 2차원 (가로 **와** 세로, 행과 열 동시에) |
| 적합한 상황 | "이 줄에 있는 요소들을 어떻게 배치할까" | "여러 줄, 여러 칸으로 된 표 같은 배치를 어떻게 할까" |
| 이 프로젝트 사용처 | 네비게이션 바, 버튼 안 아이콘+텍스트, 카드 안 세로 정렬 | 프로젝트 카드 그리드, 스킬 카드 그리드 |

이 판단 기준을 실제로 적용한 두 곳을 보겠습니다.

### 2-2. Flexbox — 네비게이션 바

```css
.nav {
  display: flex;
  align-items: center;
  justify-content: space-between; /* 로고는 왼쪽 끝, 메뉴는 오른쪽 끝 */
  height: 100%;
}
```
[css/style.css:225](css/style.css:225)

네비게이션은 "로고 - 메뉴 - 다크모드 버튼"이 **한 줄**에서 양 끝으로 벌어지기만 하면 됩니다. 행과 열을 따질 필요가 없는, 전형적인 1차원 배치라서 Flexbox가 정답입니다. `justify-content: space-between`은 "자식들 사이의 여백을 균등하게 벌리되, 첫 요소는 왼쪽 끝, 마지막 요소는 오른쪽 끝에 붙인다"는 뜻입니다.

### 2-3. Grid — 프로젝트/스킬 카드

```css
.projects__grid {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(280px, 1fr));
  gap: var(--space-4);
}
```
[css/style.css:539](css/style.css:539)

카드가 몇 개인지, 화면이 몇 px인지 미리 알 수 없는 상태에서 "자동으로 줄바꿈되는 카드 그리드"를 만들어야 했습니다. 이건 행과 열이 동시에 필요한 2차원 배치라서 Grid를 썼습니다. `repeat(auto-fit, minmax(280px, 1fr))`를 하나씩 풀어보면:

- `minmax(280px, 1fr)` → "각 칸은 최소 280px은 보장하고, 남는 공간이 있으면 1fr(=균등 비율)만큼 늘어난다"
- `auto-fit` → "한 줄에 들어갈 수 있는 만큼 칸(column)을 최대한 채우고, 안 들어가면 자동으로 다음 줄로 넘긴다"

이 한 줄 덕분에 **미디어 쿼리 없이도** 화면이 넓으면 카드가 3~4개씩, 좁으면 1~2개씩 자동으로 배치됩니다. (실제 줄바꿈 개수 조정은 이 자동 로직에 맡기고, 브레이크포인트는 다른 레이아웃 변경에만 사용했습니다.)

### 2-4. CSS 변수(`:root`)와 다크 모드

```css
:root {
  --color-bg: #ffffff;
  --color-navy: #13294b;
  --color-accent: #c8901f;
  /* ... */
}

[data-theme="dark"] {
  --color-bg: #0a1122;
  --color-navy: #b9cdfa;
  --color-accent: #f0c469;
  /* 같은 변수 이름, 다른 값 */
}
```
[css/style.css:47](css/style.css:47), [css/style.css:93](css/style.css:93)

색상을 `#ffffff`처럼 하드코딩하지 않고 `var(--color-bg)`처럼 변수로 쓴 이유는, **다크 모드를 "값 하나만 바꿔서" 전체 화면에 적용**하기 위해서입니다. HTML의 `data-theme` 속성만 `"dark"`로 바뀌면, 그 속성을 셀렉터로 잡고 있는 CSS 블록이 같은 변수 이름에 다른 색상값을 다시 정의해줍니다. 즉, 버튼이든 카드든 배경이든 — 코드 안에서 `var(--color-navy)`를 쓰고 있는 모든 곳이 자동으로 색이 바뀝니다. 클래스를 일일이 바꾸거나 `if (dark) { ... }` 로 요소마다 스타일을 다시 계산할 필요가 없습니다.

### 2-5. 모바일 퍼스트 + 브레이크포인트

```css
/* 기본 스타일 = 모바일 기준 */
.nav__menu { display: flex; flex-direction: column; opacity: 0; ... }

@media (min-width: 768px) {
  .nav__toggle { display: none; }
  .nav__menu { position: static; opacity: 1; flex-direction: row; }
}

@media (min-width: 1024px) {
  .hero { padding-top: calc(var(--nav-height) + var(--space-8)); }
}
```
[css/style.css:295](css/style.css:295), [css/style.css:921](css/style.css:921), [css/style.css:977](css/style.css:977)

`min-width`를 쓰는 미디어쿼리는 "이 너비 이상일 때 추가로 적용"이라는 뜻입니다. 그래서 기본 CSS를 화면이 제일 좁은 모바일 기준으로 먼저 작성하고, 화면이 넓어질 때(`768px`, `1024px`) 필요한 스타일만 얹는 방식(모바일 퍼스트)으로 짰습니다. 반대로 처음부터 데스크톱 기준으로 짜고 `max-width`로 줄여나가면, 모바일에서 안 쓸 스타일까지 먼저 로드하고 덮어써야 해서 코드가 더 꼬입니다.

## 3. JavaScript — DOM 선택과 이벤트 연결 흐름

### 3-1. querySelector로 DOM 찾기

```js
const header = document.querySelector('#header');       // 단일 요소 1개
const navLinks = document.querySelectorAll('.nav__link'); // 일치하는 요소 전부 (NodeList)
```

`querySelector`는 CSS 셀렉터와 똑같은 문법(`#id`, `.class`, `tag`)으로 요소를 찾되, **일치하는 것 중 첫 번째 하나만** 돌려줍니다. `querySelectorAll`은 일치하는 걸 **전부** NodeList(배열과 비슷한 목록)로 돌려줍니다. 그래서 "버튼 하나"는 `querySelector`, "메뉴 링크 여러 개"는 `querySelectorAll` + `forEach`로 순회하는 식으로 나눠 썼습니다.

### 3-2. addEventListener로 이벤트 연결하기

`addEventListener(이벤트종류, 실행할함수)` 형태로, "이 요소에서 이 이벤트가 발생하면 이 함수를 실행해라"를 등록하는 함수입니다. HTML에 `onclick="doSomething()"`처럼 직접 쓰지 않고 JS 파일에서만 연결한 이유는, **HTML(구조)과 JS(동작)를 분리**하기 위해서입니다. 이렇게 하면 HTML을 수정할 때 JS 코드를 건드릴 일이 없고, 하나의 요소에 이벤트를 여러 개 붙이는 것도 가능합니다.

### 3-3. 실제 흐름 하나 끝까지 따라가기 — 햄버거 메뉴

```js
const navToggle = document.querySelector('#navToggle'); // ① DOM 선택
const navMenu = document.querySelector('#navMenu');

navToggle.addEventListener('click', () => {              // ② 이벤트 등록
  const isOpen = navMenu.classList.toggle('is-open');    // ③ 클릭 시 실행: 상태 토글
  navToggle.classList.toggle('is-active', isOpen);
  navToggle.setAttribute('aria-expanded', String(isOpen));
});
```
[js/main.js:40](js/main.js:40)

1. **DOM 선택**: 버튼과 메뉴 요소를 변수에 담아둔다.
2. **이벤트 등록**: "클릭되면 이 함수를 실행해라"를 브라우저에 등록해둔다. (아직 실행 안 됨, 대기 상태)
3. **사용자가 클릭** → 브라우저가 등록해둔 함수를 실행 → `classList.toggle('is-open')`이 클래스를 붙였다 뗐다 하면서 **불리언 상태**처럼 동작
4. CSS에서는 `.nav__menu.is-open { opacity: 1; ... }`처럼 그 클래스가 있을 때만 적용되는 스타일을 미리 정의해뒀기 때문에, **클래스가 바뀌는 순간 화면이 바뀐다.**

즉 "JS는 클래스만 갈아끼우고, 실제 시각적 변화는 CSS가 담당"하는 구조입니다. 이렇게 역할을 나누면 애니메이션 디테일(속도, 이징 등)은 CSS `transition`만 수정하면 되고, JS는 로직에만 집중할 수 있습니다.

### 3-4. `event.preventDefault()`가 필요한 이유

`<a href="#about">`는 원래 클릭하면 브라우저가 즉시(애니메이션 없이) 해당 위치로 점프합니다. 부드러운 스크롤을 JS로 직접 구현하려면 이 **기본 동작을 먼저 막아야** 합니다.

```js
link.addEventListener('click', (event) => {
  const targetEl = document.querySelector(targetId);
  if (!targetEl) return;

  event.preventDefault();                                   // 기본 점프 동작 차단
  targetEl.scrollIntoView({ behavior: 'smooth', block: 'start' }); // 직접 부드럽게 이동
});
```
[js/main.js:55](js/main.js:55)

마찬가지로 `<form>`의 기본 submit은 "페이지 새로고침"이기 때문에, 유효성 검사 로직을 실행하려면 `contactForm.addEventListener('submit', (event) => { event.preventDefault(); ... })`로 그 기본 동작부터 막아야 합니다([js/main.js:352](js/main.js:352)).

## 4. ES6+ 문법 — 왜 이 문법들을 썼는가

### 4-1. 화살표 함수

```js
const renderFeaturedProjects = (filter = 'all') => { ... };
filterButtons.forEach((btn) => { ... });
```

`function` 키워드로 쓰는 것 대비 코드가 짧고, 특히 `map`/`filter`/`forEach`처럼 **함수를 인자로 넘기는 상황**에서 `array.map(function(x) { return ... })`보다 `array.map((x) => ...)`가 훨씬 간결합니다. 콜백 함수가 많은 이 프로젝트(이벤트 핸들러, 배열 변환 함수)에는 화살표 함수가 잘 맞습니다.

### 4-2. 구조분해 할당(Destructuring)

```js
const createRepoCard = ({ name, description, html_url: htmlUrl, language, stargazers_count: stars }) => `
  <h4>${name}</h4>
  <p>${description || '설명이 등록되지 않은 저장소입니다.'}</p>
`;
```
[js/main.js:257](js/main.js:257)

GitHub API가 돌려주는 저장소 객체는 필드가 20개가 넘습니다. 그중 실제로 쓰는 필드 5개만 함수 매개변수 자리에서 바로 꺼내 쓴 겁니다. `repo.name`, `repo.description`처럼 매번 `repo.`을 반복하지 않아도 되고, **함수 시그니처만 봐도 "이 함수가 어떤 데이터를 필요로 하는지"가 한눈에 드러난다**는 장점이 있습니다. `html_url: htmlUrl`처럼 콜론을 쓴 부분은 "API 필드명은 `html_url`이지만, 내 코드에서는 카멜케이스인 `htmlUrl`로 쓰고 싶다"는 별칭(rename) 문법입니다.

### 4-3. 배열 메서드 — map / filter / forEach 구분

세 가지 모두 배열을 순회한다는 점은 같지만, **무엇을 리턴하는지**가 다릅니다.

| 메서드 | 리턴값 | 이 프로젝트에서 쓴 곳 | 쓴 이유 |
| --- | --- | --- | --- |
| `map` | 각 원소를 변환한 **새 배열** | `featuredProjects.map(createProjectCard)` | 프로젝트 데이터 배열 → 카드 HTML 문자열 배열로 "1:1 변환"이 필요했음 |
| `filter` | 조건을 통과한 원소만 남긴 **새 배열** | `featuredProjects.filter(p => p.category === filter)` | 카테고리 버튼 클릭 시 "일부만 골라내기"가 필요했음 |
| `forEach` | 없음(`undefined`) | `filterButtons.forEach(btn => btn.addEventListener(...))` | 배열 각각에 "이벤트 리스너 등록"이라는 부수효과만 실행하면 됐고, 새 배열이 필요 없었음 |

`map`으로 만든 HTML 문자열 배열은 `.join('')`으로 하나의 문자열로 합친 뒤 `innerHTML`에 대입합니다:

```js
featuredGrid.innerHTML = filtered.map(createProjectCard).join('');
```

배열 상태로 두면 브라우저가 이해 못 하므로, 최종적으로는 문자열로 합쳐서 DOM에 넣어야 합니다.

## 5. 비동기 처리 — fetch, async/await, 4가지 상태

### 5-1. 왜 "비동기"가 필요한가

`fetch`로 GitHub 서버에 요청을 보내면 응답이 올 때까지 몇 백 ms가 걸립니다. 만약 이걸 동기적으로(순서대로 딱 멈춰서) 처리하면 응답 오는 동안 화면 전체가 멈춰버립니다. 그래서 JS는 네트워크 요청을 **비동기**로 처리하고, `async`/`await`는 "비동기 코드를 마치 동기 코드처럼 순서대로 읽히게" 해주는 문법입니다.

```js
const loadRepos = async () => {
  renderSkeleton();                    // ① 요청 보내기 전, 로딩 UI부터 표시
  setRepoStatus('불러오는 중...');

  try {
    const response = await fetch(`https://api.github.com/users/${GITHUB_USERNAME}/repos?sort=updated&per_page=6`);
    if (!response.ok) {
      throw new Error(response.status === 403 ? 'rate-limit' : 'fetch-error');
    }
    const repos = await response.json();

    if (repos.length === 0) {          // ③ 성공했지만 데이터가 없는 경우
      setRepoStatus('표시할 프로젝트가 없습니다.');
      return;
    }
    repoGrid.innerHTML = repos.map(createRepoCard).join('');  // ③ 성공
  } catch (error) {                    // ④ 실패
    setRepoStatus('프로젝트를 불러올 수 없습니다. (재시도 버튼 포함)', true);
  }
};
```
[js/main.js:271](js/main.js:271)

`await`가 붙은 줄은 "이 작업이 끝날 때까지 기다렸다가 다음 줄로 넘어가라"는 뜻입니다. `.then().then()`으로 콜백을 계속 이어붙이는 방식보다 위에서 아래로 읽히는 순서가 실제 실행 순서와 같아서 가독성이 좋습니다.

### 5-2. try/catch로 실패를 붙잡는 이유

네트워크 요청은 **반드시 실패할 수 있는 코드**입니다 (인터넷 끊김, GitHub 서버 오류, 시간당 60회 제한 초과 등). `try` 블록 안에서 에러가 발생하면(직접 `throw`한 것 포함) 나머지 `try` 코드는 건너뛰고 바로 `catch` 블록으로 넘어갑니다. 이 구조 덕분에 API가 실패해도 자바스크립트 실행 자체가 멈추지 않고, **사용자에게 실패했다는 걸 UI로 보여주고 재시도할 기회**를 줄 수 있습니다.

### 5-3. 4가지 상태 → 4가지 화면

| 상태 | 트리거 | 화면 |
| --- | --- | --- |
| 로딩 | 요청 시작 직후 | 스켈레톤 카드 3개 + "불러오는 중" 텍스트 |
| 성공 | `response.ok`이고 데이터 있음 | 실제 저장소 카드 렌더링 |
| 빈 상태 | `response.ok`이지만 `repos.length === 0` | "표시할 프로젝트가 없습니다" |
| 에러 | `response.ok`가 false, 또는 네트워크 자체 실패 | "불러올 수 없습니다" + 재시도 버튼 |

이 4가지를 **하나의 함수 안에서 분기**시킨 이유는, 실제 서비스에서 API 연동은 항상 이 4가지 경우의 수를 다 처리해야 하기 때문입니다 (성공만 가정하고 짜면 로딩 중 빈 화면이 뜨거나, 실패 시 흰 화면만 남는 문제가 생김).

## 6. "이벤트 → 상태 → 렌더링" 하나로 끝까지 보기 — 다크 모드

이 프로젝트에서 요구한 핵심 개념이자, React의 `state` 개념으로 이어지는 부분입니다. 다크 모드 토글 하나를 끝까지 분해하면 이렇습니다.

```js
// 상태를 어디에 저장하는가 → HTML의 data-theme 속성 + localStorage
const root = document.documentElement;
const themeToggle = document.querySelector('#themeToggle');

themeToggle.addEventListener('click', () => {                        // 1) 이벤트 발생
  const current = root.getAttribute('data-theme') === 'dark' ? 'dark' : 'light';
  const next = current === 'dark' ? 'light' : 'dark';                 // 2) 다음 상태 계산

  root.setAttribute('data-theme', next);                              // 3) 상태 변경 (DOM 속성)
  localStorage.setItem('theme', next);                                // 3) 상태 저장 (새로고침 대비)
  applyThemeIcon(next);                                                // 4) 렌더링 갱신 (아이콘 모양)
});
```
[js/main.js:28](js/main.js:28)

단계별로 보면:

1. **이벤트**: 사용자가 버튼을 클릭한다.
2. **상태 계산**: "지금 라이트면 다크로, 다크면 라이트로" 다음 상태를 결정한다. 이 프로젝트에서 "상태"는 별도의 변수가 아니라 `<html data-theme="...">` 속성 값 그 자체입니다.
3. **상태 반영**: `setAttribute`로 실제 DOM에 상태를 써넣고, `localStorage`에도 같은 값을 저장해서 새로고침해도 상태가 유지되게 한다.
4. **렌더링(화면 갱신)**: CSS가 `[data-theme="dark"]` 셀렉터를 통해 변수 값을 다시 정의해뒀기 때문에, 속성값이 바뀌는 즉시 배경색·글자색 등 화면 전체가 다시 그려진다. 아이콘(달/해)은 CSS만으로는 바꿀 수 없는 부분이라 `applyThemeIcon()`에서 `classList.toggle`로 직접 바꿔준다.

페이지를 새로고침해도 테마가 유지되는 이유는 `<head>`에 있는 아주 작은 인라인 스크립트 때문입니다:

```html
<script>
  (() => {
    const saved = localStorage.getItem('theme');
    const prefersDark = window.matchMedia('(prefers-color-scheme: dark)').matches;
    const theme = saved || (prefersDark ? 'dark' : 'light');
    document.documentElement.setAttribute('data-theme', theme);
  })();
</script>
```
[index.html:16](index.html:16)

이 스크립트는 `<link rel="stylesheet">`보다도 먼저, CSS가 로드되기 전에 실행되도록 `<head>` 최상단에 둡니다. 이렇게 안 하면 "일단 라이트 모드로 그렸다가 0.1초 뒤 JS가 실행되며 다크로 바뀌는" 깜빡임(FOUC, Flash of Unstyled Content)이 생기기 때문입니다.

이 흐름은 다른 3가지 기능에도 똑같이 반복됩니다.

- **GitHub API**: 이벤트(=페이지 로드) → 상태(로딩/성공/에러/빈) → `repoGrid.innerHTML` 갱신
- **폼 유효성 검사**: 이벤트(=입력/제출) → 상태(필드별 valid/invalid) → 에러 메시지 표시·숨김
- **프로젝트 필터**: 이벤트(=필터 버튼 클릭) → 상태(`dataset.filter` 값) → `featuredGrid.innerHTML` 재계산

React를 배우면 이 "상태가 바뀌면 화면이 알아서 다시 그려진다"는 패턴을 `useState` + JSX가 자동으로 대신 해주는데, 지금은 그 자동화를 `classList`/`setAttribute`/`innerHTML`로 직접 손으로 짠 것이라고 이해하면 됩니다.
